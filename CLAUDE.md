# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A single-file MCP server (`perforce_alm_mcp.py`) that wraps the Perforce ALM (formerly Helix ALM / TestTrack) REST API and exposes it to MCP clients via the Model Context Protocol. Item coverage includes requirements, documents (with trees and snapshots), test cases, automation suites with build results, and issues; see the **Tool-specific notes** section below and `README.md` for the full tool inventory.

## Running the Server

```powershell
python perforce_alm_mcp.py    # or `py perforce_alm_mcp.py` depending on the Python install
```

The server speaks MCP over stdio via `FastMCP` (the standalone `fastmcp` 3.x package), so the launch command blocks indefinitely waiting on stdin — it's meant to be spawned by an MCP client (Claude Desktop / Claude Code), not run interactively.

The server is also packaged (`pyproject.toml`, setuptools backend) with a `perforce-alm-mcp` console-script entry point (`perforce_alm_mcp:main`), so it can run via `uvx perforce-alm-mcp` (once on PyPI) or `uvx --from git+<url> perforce-alm-mcp` (from GitHub), and be built/shipped as a Docker image — see `README.md`. The package version is read dynamically from `_MCP_VERSION` (via `[tool.setuptools.dynamic]`), so bump only that constant.

Quick syntax/import check:

```powershell
python -c "import perforce_alm_mcp"
```

There is no lint config. Validate behavioral changes by running the server and exercising tools through an MCP client.

This server never writes configuration to disk itself. `_config` lives only in process memory, seeded once at import from environment variables — optionally falling back to a caller-supplied `PERFORCE_ALM_MCP_CONFIG_FILE` (see **Bootstrap flow** below) — and never reconfigured at runtime except for username/password via `set_basic_credentials`. `export_mcp_entry` returns the current settings as a `{"command", "args", "env"}` shape on demand, redacting the API key id/secret since a tool response can flow into the AI's own context — see that tool's docstring for the full reasoning.

## Dependencies

Python 3.13+. Install with:

```powershell
pip install .
```

Dependency versions in `pyproject.toml` (`[project.dependencies]`) are **exact pins** (`==`), not floors — the single source of truth for every install path (`pip install .`, `uvx`, `uvx --from git+<url>`, and the Docker image), none of which consult a lock file. A `>=` floor here means "whatever is newest on PyPI at install time," not a tested version. This was previously floor-based (`fastmcp>=3.2.4`, etc.) and it bit the project directly: `fastmcp>=3.2.4` resolved to `3.4.6` during a routine `requirements.txt` regeneration, pulling in a `fastmcp-slim` transitive dependency that doesn't exist at `3.2.4` and had never been tested against this codebase. Raised again as a broader supply-chain risk: floor-only constraints mean no two installations are identical (harder incident response), a compromised upstream release is adopted automatically with no human decision, and any point-in-time snapshot (Mend scan, `requirements.txt`) describes only what existed at export time, not what a given customer actually installed. Bump a pin deliberately, one version at a time — never widen it back to a floor — and regenerate `uv.lock` and `requirements.txt` in the same commit.

`requirements.txt` (generated via `uv export --no-emit-project --format requirements-txt -o requirements.txt`) is checked into both Surround and git, and now serves two purposes: Mend SCA scanning, and — via `pip install --require-hashes -r requirements.txt` in the `Dockerfile` — the Docker image's hash-verified dependency install, so a build fails loudly rather than silently accepting bytes PyPI serves that don't match what was resolved into `uv.lock`. `--no-emit-project` is required: without it, `uv export` emits this project itself as an unhashed `-e .` editable line alongside the hashed third-party pins, which pip rejects outright (`cannot be installed when requiring hashes, because there is no single file to hash` — pip requires every line to have a hash once any line does, and an editable install can never be hashed). It is not a dependency source and should not be hand-edited; regenerate it (and `uv.lock`) whenever `pyproject.toml`'s dependencies change — a stale `requirements.txt` would silently keep installing old, already-superseded versions into the Docker image rather than fail loudly.

Version constraints:
- `fastmcp==3.2.4` — the server framework (standalone FastMCP 3.x; provides `from fastmcp import FastMCP` and the middleware API). Pulls `mcp` in transitively.
- `pydantic==2.12.0` — only `BeforeValidator`, used by the `Json*` parameter aliases (see **Optional structured parameters** below). Already pulled in transitively via `fastmcp`, but declared explicitly here because the module now imports it directly. Pinned to `2.12.0` rather than the `fastmcp`-era `2.11.7`: `mcp==1.28.1` requires `pydantic>=2.11.0` on Python <3.14 but `>=2.12.0` on Python >=3.14, and this project supports both, so `2.12.0` is the lowest single version satisfying both branches.
- `mcp==1.28.1` — pulled in transitively via `fastmcp`, but pinned directly to force the fix for CVE-2026-59950 (missing Host/Origin validation in the deprecated `mcp.server.websocket.websocket_server` transport, fixed in `1.28.1`). Not exploitable as deployed (this server only uses the stdio transport), but Mend flags the resolved version regardless.
- `opentelemetry-sdk==1.41.1` and `opentelemetry-exporter-otlp-proto-grpc==1.41.1` — telemetry export over OTLP/gRPC (pulls in `grpcio`); only exercised when telemetry is enabled (see **Telemetry**). These two ship from the same upstream release train and are only tested against each other within the same minor version — bump both together, never independently.

REST calls to Perforce ALM use only stdlib (`urllib`) — no `requests`.

## Testing

A `pytest` suite lives in `tests/` (`tests/test_*.py`), with shared fixtures and helpers at the repo root:

- `conftest.py` — the autouse `reset_state` fixture snapshots and restores the mutable module globals (`_config`, `_current_project`) around every test so state can't leak between tests; if you add a new mutable module global to `perforce_alm_mcp.py` (a cache, a compiled SSL context, etc.), extend `reset_state` to cover it too. It also provides three fixtures: `token_req` / `non_token_req` patch the two HTTP helpers (`_token_authenticated_request` / `_non_token_authenticated_request`) so a test asserts the request a tool built (`method, path` positional; `body` keyword) without a live network call, and `project` activates a project (`PROJ`) so token-scoped tools pass the active-project gate — pair it with `token_req`.
- `_test_helpers.py` — `tool_fn("<tool_name>")` returns the plain underlying callable for an `@mcp.tool()`-decorated function (robust to fastmcp's `decorator_mode`). Bind it at module-import time, e.g. `get_requirement = tool_fn("get_requirement")`, then call the tool directly. It lives separate from `conftest.py` because importing the conftest plugin module directly is unsafe. **Caveat**: `tool_fn()` calls the raw Python function directly, bypassing FastMCP's pydantic argument validation entirely — fine for asserting a tool's own logic (envelope wrapping, error strings, path building), but it cannot exercise anything that lives in the validation layer itself (e.g. the `Json*` alias coercion described in **Optional structured parameters** above). `tests/test_json_coercion.py` instead drives the real `FunctionTool` object — `await mcp.get_tool(name)` then `await tool.run(kwargs)` (wrapped in a small `asyncio.run` helper since the rest of the suite is sync) — because that's the only path that actually runs pydantic validation.

Run the suite from this directory:

```powershell
python -m pytest                                                                # whole suite
python -m pytest tests/test_requirements.py                                     # one file
python -m pytest tests/test_requirements.py::test_default_args_send_empty_body  # one test
```

(`python -m pytest` rather than a bare `pytest` so it runs whether or not the Scripts directory is on PATH.)

`pytest` is required to run the suite and is intentionally **not** a runtime dependency in `pyproject.toml`; install it with `pip install -r requirements-dev.txt`.

Running `pytest` is also the real syntax gate for the whole repo — the `python -c "import perforce_alm_mcp"` import check loads only the main module and won't catch errors in the test files themselves.

**Keep tests in sync with the tools.** When a tool's signature or behavior changes, update its matching test in the same change — the same discipline as keeping the **Tool overview** table in `README.md` current. A test that still asserts old behavior is silent drift until the suite is next run.

## Architecture

**Single-file design**: all tools, helpers, and server setup live in `perforce_alm_mcp.py`.

**Tool-call protocol**: The `FastMCP(instructions=...)` block at the top of the file gates all work behind config + active project — clients are told to ask the user for connection details (REST API URL, port, auth type, credentials, or a `PERFORCE_ALM_MCP_CONFIG_FILE` path) and set them as environment variables, restarting the server, if any are missing → `get_active_project`, falling back to `list_projects` + `select_project` if no project is active, before any other tool. If `auth_type` is `"basic"` and no username/password are loaded for the session, the instructions tell clients to call `set_basic_credentials` for credential entry instead of restarting the server. There is no tool that reconfigures the connection at runtime — connection settings are environment-variable-only by design. A prior version of this server had a `configure_perforce_alm` tool that accepted an arbitrary `rest_api_url` argument and sent the configured credential to it; it was removed after a security review found that a prompt injection could exploit it to redirect the credential to an attacker-controlled host. When adding a new item-level tool, assume `_current_project` is already set; do not re-implement the gating. The instructions text is built by `_build_instructions()` rather than hardcoded as a static literal, so it stays easy to keep in sync with the env var names it references.

**Bootstrap flow:**
- `_config` dict is populated at import time via `_env_setting(key, default)` for each field — a direct env var wins, else the value of that same key from `_load_config_file_env()` (the `env` block of the file at `PERFORCE_ALM_MCP_CONFIG_FILE`, if that var is set and the file is readable/well-formed; a missing/bad file is silently treated as empty, not an error), else `default`. This is the server's *only* read-side persistence mechanism, and it's entirely caller-driven: this server never writes that file itself (see below), so it only ever reflects whatever a caller previously saved from an `export_mcp_entry` response (or hand-wrote itself).
- `_config` is never reconfigured at runtime, except for username/password via `set_basic_credentials` — every other setting is fixed for the process's lifetime once seeded at import. Basic auth (`username` / `password`) is intentionally session-only regardless — supplied via `PERFORCE_ALM_USERNAME` / `PERFORCE_ALM_PASSWORD` env vars (or the config file fallback) at import, or via `set_basic_credentials` mid-session. Only `username` is required; `password` may be empty for an account configured without one. `set_basic_credentials` verifies the supplied credentials against the server (a `GET /projects` call) before committing them — a 401/403, or any other verification failure (e.g. an unreachable server), returns an "Error:" and rolls `_config["username"]`/`["password"]` back to whatever was in effect before the call, so a failed verification never overwrites working credentials with untested ones. `_build_server_entry()` does not emit these two env vars at all, so they never appear in `export_mcp_entry`'s output.
- Bearer tokens (project-scoped) live in `_config["access_token"]` / `_config["token_expires_on"]`, in-memory only. `_get_token()` refreshes them on demand via `GET /{projectID}/token` and caches the result in `_config` for reuse until expiry. This server has no disk-persistence mechanism for the token at all — it is deliberately never written anywhere, not even to a caller-saved config file (`_build_server_entry()` never emits it, so there's nothing to save).
- Net effect: every new session fetches a fresh token from the server; there is no cross-session token reuse. Within a session, the cached token is reused until it expires (or until `refresh_token`/`select_project` clears it).
- The `mcpServers` key used when building an entry is `_SERVER_NAME` (default `"Perforce ALM"`, overridable via the `PERFORCE_ALM_MCP_SERVER_NAME` env var), so multiple installs can coexist under different names without code changes — and so `_load_config_file_env()` knows which key to read back out of a caller-saved file.
- Force-rotation: the `refresh_token` tool discards the cached token and fetches a new one via `_get_token()`. Useful when the ALM Server has been restarted (the cached token is dead server-side but its local `token_expires_on` hasn't lapsed yet, so `_get_token()` would keep returning the stale value on its own).

**Session project state**: `_current_project` (module-level `str`) is the live active project for the session — seeded from `PERFORCE_ALM_DEFAULT_PROJECT` at import, updated by `select_project`. `_config["default_project"]` is a separate field that just preserves the original env value when re-writing config files; runtime tools should always read `_current_project`.

**Key helpers:**
- `_create_authorization_header()` — returns `"Basic <base64(user:pass)>"` or `"ApiKey <id>:<secret>"` (API-key form is sent raw, not base64-encoded) depending on `_config["auth_type"]`
- `_create_base_restapi_url()` — returns `https://<url>:<port>/helix-alm/api/v0`; prefixes `https://` automatically if `_config["url"]` has no scheme. Uses the legacy `helix-alm` path segment (not `perforce-alm`) for backward compatibility — ALM 2026.1+ rewrites `helix-alm` → `perforce-alm` server-side, so `helix-alm` works on every version while `perforce-alm` works only on 2026.1+
- `_non_token_authenticated_request(method, path, timeout=_HTTP_TIMEOUT)` — uses `_create_authorization_header()` (API key or Basic). Use ONLY for `/projects`, `/versions`, and `/{projectID}/token`. No body parameter; always call with `"GET"` — the function accepts any method string but can't send a body, so it's GET-only by convention, not by enforcement.
- `_token_authenticated_request(method, path, body=None, timeout=_HTTP_TIMEOUT)` — uses `Bearer <token>` from `_get_token()`. Use for ALL project-scoped endpoints (requirements, documents, issues, etc.)
- `_token_authenticated_request_with_status(method, path, body)` — same request shape, but returns `(dict, status)` so the caller can detect a 206 partial-success PUT/POST. Hand-builds the request rather than adding a flag to `_token_authenticated_request` itself, to avoid touching that function's shared dict-only return contract. Used by the four `update_*` tools and the four `create_*` tools (see the folders-non-atomicity notes above) — every other project-scoped call uses the plain `_token_authenticated_request`.
- `_get_token()` — returns a cached Bearer token for `_current_project`, refreshing via `GET /{projectID}/token` when expired
- `_build_server_entry()` — builds the `{"command", "args", "env"}` dict from `_config`, returned by `export_mcp_entry` for the caller to write wherever it wants — this server itself never writes it anywhere. The `command`/`args` come from `_launch_invocation()`: they default to `python <abs path to this script>` (correct for native installs) but are overridable via `PERFORCE_ALM_MCP_LAUNCH_COMMAND` / `PERFORCE_ALM_MCP_LAUNCH_ARGS` (JSON array). This exists because inside Docker (or uvx) `__file__` is a container-internal/transient path the host can't launch, so the deployer must declare the real host invocation; the two override vars are deliberately kept out of the emitted `env` block.
- `_load_config_file_env()` / `_env_setting()` — the read-side counterpart to `_build_server_entry()`; see **Bootstrap flow** above. Only called at import time to build the initial `_config`, never afterward.
- `_valid_projects(data)` — filters a `/projects` response down to entries with an `id` (used by `select_project`)

**Telemetry (OpenTelemetry)**: Perforce-controlled. Gated by `_TELEMETRY_ENABLED` (bool) and the resolved OTLP endpoint — both currently ship **off for development**: `_TELEMETRY_ENABLED = False` and `_OTEL_ENDPOINT = ""`, with the shipped default (`https://grpc.public.prd.shared.perforce.com`) sitting commented right below the constant. Flip the bool to `True` and uncomment the endpoint to turn it on. `_resolve_otel_endpoint()` picks the effective endpoint in precedence order — `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, then `OTEL_EXPORTER_OTLP_ENDPOINT`, then the compiled `_OTEL_ENDPOINT` — so the Perforce Agentic Gateway (or any operator) can redirect export at runtime, falling back to the compiled default. `_init_telemetry()` — called from `__main__` before `mcp.run()` — activates only when `_TELEMETRY_ENABLED and _resolve_otel_endpoint()` are both truthy, installing a `TracerProvider` (resource attrs `service.name=perforce-alm-mcp`, `service.version=_MCP_VERSION`) with the **OTLP/gRPC** `OTLPSpanExporter` (`opentelemetry.exporter.otlp.proto.grpc`); otherwise the OTel SDK is never imported. **gRPC only** — the endpoint is a gRPC target (no `/v1/traces` path) and a non-gRPC `OTEL_EXPORTER_OTLP_PROTOCOL` is intentionally not honored, though the exporter still reads the other `OTEL_EXPORTER_OTLP_*` vars (headers, timeout, TLS). Nothing telemetry-related is ever written to disk by this server — the OTel env vars are only read from the process environment. `_TelemetryMiddleware.on_call_tool` emits one **SERVER** span per tool call using the MCP OTel semantic conventions (`mcp.method.name`, `gen_ai.tool.name`, `gen_ai.operation.name=execute_tool`, coarse `error.type`, `network.transport=pipe`) plus `mcp.client.name`/`mcp.client.version` from the initialize handshake, and adopts inbound W3C trace context from the request `_meta` (`traceparent`/`tracestate`). **No tool arguments, results, or error messages are ever recorded** — `error.type` is a coarse category from `_classify_error` (auth_failed / not_found / rate_limited / timeout / tool_error), derived from this server's `"Error:"`-string return convention. New tools are instrumented automatically by the middleware — nothing to add per tool. Gotcha: in fastmcp 3.x, user middleware runs *outside* fastmcp's own built-in tool span, so we create our own span rather than enriching theirs.

**Adding new tools**: Decorate with `@mcp.tool(annotations=_X)`, wrap in `try/except Exception as e`, and follow the **Tool output conventions** below (error string on failure, `json.dumps(data, indent=2)` on success). Pick the right HTTP helper (see **Key helpers**): `_token_authenticated_request()` for any project-scoped path (the common case), `_non_token_authenticated_request()` only for `/projects`, `/versions`, or `/{projectID}/token`. Build query strings into `path` with `urllib.parse.urlencode` rather than extending the helpers. See `get_versions()` for a minimal pattern and `get_requirements_by_query()` for one with query params and Bearer-token use. Bump `_MCP_VERSION` in the script for significant changes — it's returned by the `get_versions()` tool alongside the REST API version. `_token_authenticated_request()` raises via `_get_token()` if `_current_project` is empty, so item-level tools don't need their own gate — the FastMCP `instructions` block + this error are the gate. Whenever a tool is added, renamed, or removed, update the **Tool overview** table in `README.md` to match (the table lists tools by category; it intentionally carries no counts, so only the tool names need maintaining).

**Tool annotations**: every `@mcp.tool()` must pass `annotations=`, set to one of the constants defined near the top of the module, right after the `Json*` aliases. Without this, an MCP client cannot tell a read from a bulk write or an automation trigger when deciding whether a tool call needs human approval — a bare `@mcp.tool()` silently reintroduces that problem, so never add one without picking a constant first. The constants:
- `_READ_ONLY` — calls the ALM REST API but changes nothing (`get_*`, `list_*`).
- `_READ_ONLY_LOCAL` — same, but touches no network at all (`get_active_project`, `export_mcp_entry`).
- `_SESSION_STATE` — changes only this server's own in-memory session state (`set_basic_credentials`, `select_project`, `refresh_token`).
- `_WRITE_ADDITIVE` — mints a new, independent record each call (`create_*`, `upload_*_attachment`).
- `_WRITE_ASSOCIATIVE` — mutates a set-membership or association rather than an independent record, so replaying the same call again leaves the same end state (`add_automation_suite_testcases`, `associate_automation_results`).
- `_WRITE_DESTRUCTIVE` — can wholesale-replace or delete existing Perforce ALM data (`update_*`, `remove_automation_suite_testcase`).
- `_WRITE_DESTRUCTIVE_UNSAFE_RETRY` — same as `_WRITE_DESTRUCTIVE`, but retrying an identical call is not safe (`update_issues`: a `foundByRecords` entry without an `id` is always treated as a new addition, so a retry adds a duplicate record instead of converging).
- `_LOCAL_FILE_WRITE` — writes to the machine running this server, not to Perforce ALM (`download_attachment`, whose `overwrite` argument can overwrite an existing local file). `destructiveHint=False` because no ALM data is ever touched — kept out of the `_WRITE_DESTRUCTIVE` family so that name reliably means "destroys ALM data"; `readOnlyHint=False` because it's not a no-op locally.
- `_TRIGGER` — kicks off an external, non-idempotent side effect beyond a data write (`run_automation_suite`).

If none of these fit a new tool's actual behavior, add a new constant following the same pattern rather than reaching for the closest existing one — the annotation must describe what the tool actually does, not just what's already defined.

**Optional structured parameters (`Json*` aliases)**: the rule is general, not tied to today's five alias names — never annotate an *optional* parameter (a `| None` union) whose other branch is a container type (`list`, `dict`, `set`, or `tuple`, at any element-type specificity) as a bare type. Instead its annotation must carry `Annotated[<type>, BeforeValidator(_coerce_json)]`. Today that's satisfied by one of the existing aliases — `JsonObj` (`dict | None`), `JsonObjList` (`list[dict] | None`), `JsonStrMap` (`dict[str, str] | None`), `JsonStrList` (`list[str] | None`), `JsonMixedList` (`list[str | int] | None`, used by `list_automation_suite_builds`) — but the set of aliases is not exhaustive by design: if a new tool needs an optional container of a shape none of these cover (e.g. `list[int] | None`), add a new alias following the exact same pattern (e.g. `JsonIntList = Annotated[list[int], BeforeValidator(_coerce_json)]`) rather than falling back to the bare type because "no alias matches yet." Root cause: pydantic/fastmcp renders an `Optional` type as `anyOf: [<branch>, {"type": "null"}]`, which leaves no top-level `"type"` key on the parameter's schema (it's nested inside the `anyOf` branches instead). At least one real MCP client (Claude Code) decides how to marshal an argument by checking for a top-level `"type"`, and falls back to sending a JSON-stringified value when it doesn't find one — which a bare `dict`/`list` annotation then rejects (`pydantic.ValidationError`, `dict_type`/`list_type`, `input_type=str`), even though a *required* (non-`Optional`) array/object param is unaffected (no `anyOf`, so the client sees the type directly). `_coerce_json` parses a JSON string into the real value before pydantic's own type validation runs, transparently recovering a stringified argument while leaving the advertised schema byte-identical (verified: a `BeforeValidator` doesn't change `TypeAdapter(...).json_schema()` output) — well-behaved clients that already send real objects/arrays are unaffected. `update_testcase_steps`'s `steps_data: dict` (required, no `| None`) is the reference case that was never broken and needs no alias. This rule is enforced structurally, not just by convention: `tests/test_json_alias_audit.py` AST-scans every `@mcp.tool()` function and fails if any optional container parameter's annotation lacks a `BeforeValidator(_coerce_json)` — checked semantically (any alias bound to `_coerce_json`), so a newly added alias like the hypothetical `JsonIntList` above needs no change to that test. When adding a new tool with an optional structured parameter, reach for a `Json*` alias (existing or newly added) by default rather than a raw `Optional` type — don't reintroduce this failure mode one tool at a time.

**Tool output conventions**: All `@mcp.tool()` functions follow project-wide shape rules so the LLM can chain them confidently.
- **Success** returns `json.dumps(response, indent=2)`. Most tools pass the REST API response through verbatim (just the parsed JSON body, no extra wrapper). A handful synthesize their own shape — bootstrap/session tools like `get_versions`, `export_mcp_entry`, `select_project`, `get_active_project`, `refresh_token`. The `list_*_attachments`/`upload_*_attachment` tools are a narrower exception: they pass the response through but strip the unusable `content` href first (see the **Attachments** note below).
- **Errors** return plain strings of the form `"Error: <message>"`, NOT JSON. Don't convert just one tool to JSON-shaped errors — it's a project-wide convention and inconsistency hurts the LLM more than the prose-vs-JSON asymmetry.
- **Chainable IDs**: items in any list response carry their canonical ID under the key `id` (integer). When feeding `*_by_query` or `list_*` results into a follow-up tool, extract `id` from each entry.
- **Bulk envelopes are auto-wrapped on input**: REST endpoints expect outer envelopes named `requirements`/`testCases` (no `Data` suffix) for bulk creates/updates. Sub-objects use the `*Data` suffix (`foldersData`, `linksData`, `stepsData`, etc.). Automation-suite endpoints are the exception — they use `automationSuitesData` and `snapshotsData` at the top level. The `update_*` tools (`update_requirements`, `update_testcases`, `update_issues`, `update_documents`) accept a plain `list[dict]`. The `create_*` tools (`create_requirements`, `create_testcases`, `create_documents`, `create_issues`) instead take single-item arguments (`fields`, `folders`, …) and wrap them into a length-1 list internally. **Inline links are not exposed on any create or update tool** — link management goes exclusively through the dedicated per-type link tools (`create_*_links` / `list_*_links` for `testcase`, `requirement`, `issue`, and `document`; each wraps `/{resource}/{itemID}/links`, `linksData` envelope). `create_requirements`/`create_testcases`/`create_documents` take **no** `links` argument because the REST **create (POST)** endpoints silently ignore an inline link payload anyway; `create_issues` follows the same no-`links` convention — the issue create schema *does* expose a links property, but POST silently ignores it too. `update_requirements`/`update_testcases`/`update_documents`/`update_issues` also take **no** `links` argument by deliberate design choice: the REST **update (PUT)** endpoints *do* honor inline links, but the PUT **REPLACES** the item's entire link collection wholesale (the list becomes the complete set, with no merge), and a link whose `peers` array omits the host item is silently dropped — so a single imperfect bulk update can clobber an item's links and report success. Adding links only through the additive `create_*_links` tools (which leave existing links untouched) avoids that footgun. **The same host-item requirement applies to the additive `create_*_links` tools too, not just the update-side clobber risk**: a `peers`-type link's `peers` array must include a LinkedItem for the host item itself alongside the other side(s) — a `peers` array containing only the target (e.g. `[{"itemID": 5, "itemType": "requirements"}]` when linking from an issue) silently no-ops, returning success with an empty `linksData` and creating nothing. **Editing or removing existing links is intentionally NOT supported in v1** — there is no PUT-on-links tool. A PUT on `/links` replaces an item's link collection wholesale, which could break traceability links or leave empty link objects behind; since links are a cornerstone of traceability (and link editing wasn't in the initial MCP requirements), that capability was judged too risky to ship now. Links are bidirectional, so a requirement↔test-case link can be set from either side. **None of the four `create_*` tools take an `attachments` argument**, for the same silent-ignore reason as links: the REST create endpoint discards an `attachmentsData` payload regardless of resource type, returning success but attaching nothing. This holds for `create_requirements`/`create_testcases`/`create_documents` (a garbage attachment ID silently succeeds with no attachment created, while the same call's `folders` sub-object correctly 404s on a garbage ID — proving the server validates sub-objects it actually processes) — matching the same finding already established for `create_issues`'s Issue schema (whose top-level `attachments` property, and the same property nested under a `foundByRecords` item, is likewise discarded regardless of what's sent). Add issue attachments after creation via `upload_issue_found_by_attachment` — see the **Attachments** note below. **All four `update_*` tools reject `links`, `events`, and `attachments` in an item's payload with a targeted error** (`"...cannot include [...] in an update: <reason>"`, naming the right `create_*_links`/`upload_*_attachment` tool) instead of letting them fall through to the generic `"has unknown keys"` message — `update_documents` additionally rejects `snapshots` this way (add snapshots via `create_document_snapshot`). `attachments` is rejected across **all four** resource types, not just issues: the REST **update (PUT)** endpoint silently discards an attachments payload for requirements, test cases, and documents too (returns success but changes nothing), confirmed by uploading a real attachment then PUTting both an empty list and a garbage attachment ID and observing the attachment set unchanged either way. `upload_*_attachment` (POST) is the only way to add one; there is no endpoint to edit or remove an existing attachment for any resource type.
- **Response shape docs** belong in the tool docstring under a `Response:` section. The docstring is the only place a runtime LLM caller can read at tool-call time — the OpenAPI spec at `helix-alm-rest-api\REST\api\spec\perforcealmrestapi.yaml` is a developer-side cross-reference, not available to deployed installs. Document the top-level keys at minimum; for nested or expanded sub-objects, summarize rather than enumerate every field — the spec stays authoritative for full field-level detail.

**Search-expression syntax**: The `*_by_query` tools all accept Perforce ALM search expressions. Field names are field labels that must match an existing field, but matching is **case-insensitive** (`Summary`, `summary`, and `SUMMARY` are equivalent; a misspelled or nonexistent field returns `404 Not Found: "The <name> field does not exist."`). Multi-word labels (e.g. `Multi Word Field`) must be wrapped in **double quotes** in raw `search` expressions — bare multi-word identifiers raise `400 Bad Request: "Incorrect syntax starting at '<first-word>'"`. String literals can be wrapped in **single or double quotes**. The server's parser has **no escape sequence** for a quote inside a string literal (doubling like `''` is NOT supported) — to include a literal quote, wrap the value in the *other* quote character: a value containing `'` must be double-quoted (`"Value's"`), a value containing `"` must be single-quoted (`'JSON: "{...}"'`). A value containing **both** quote characters cannot be expressed. Operators are `=`, `!=`, `contains`, `and`, `or`, plus parens. Example: `Product = 'WysiCorp' and "Multi Word Field" = 'X'`. The `filters` shorthand (a `{label: value}` dict) double-quotes labels automatically and quotes each value with whichever quote preserves any literal quote it contains — each pair becomes `"label" = 'value'` (or `"label" = "value"` when the value contains a single quote) so multi-word keys just work; a value with both quote types raises an error. Clauses are `and`-joined, and `and`-joined to `search` if both are supplied.

**Known unwrapped surfaces** (REST endpoints that exist upstream but have no MCP tool yet):
- **Test runs, folders** — whole resources, no tools. Natural next surfaces to add.
- **File attachments** — mostly wrapped now (see the attachment note under **Tool-specific notes**): `list_*_attachments` (GET) exists for requirements, documents, test cases, and issues; `upload_*_attachment` (POST) exists for requirements, documents, and test cases; `upload_issue_found_by_attachment` (POST `/issues/{itemID}/foundByRecords/{foundByRecordID}/attachments`) covers issues, whose attachments live on a found-by record rather than the issue itself; `download_attachment` (GET `/{projectID}/files/{encodedFileID}`) downloads any attachment regardless of resource type. Still unwrapped: **issue event attachments** (workflow-event sub-resource, not wrapped) and **automation-suite attachments** (no such endpoint exists at all). **Inline images in formatted-string fields are NOT in this category** — the REST API supports embedding a brand-new image directly, with no attachment or upload call needed first: a `formattedString.text` value can contain an `<img>` tag with a base64 data URI (`src="data:image/png;base64,..."`), and the server decodes it, stores it as a real file, and rewrites the tag's `src` to point at the stored file, populating `inlineImages` on read-back. This is documented directly in the `TextField` schema description in the OpenAPI spec and confirmed via `create_requirements`. It works through any `create_*`/`update_*` tool's `fields` argument today — those tools pass field values through with minimal validation, so a caller that knows the shape can already do this on any item type with a `formattedString` field (requirements, issues, test cases, documents). Inline images are tracked separately from the item's regular `attachments` collection — `list_*_attachments` does not surface them. No MCP tool documents this shape or helps construct it today; none of the `create_*`/`update_*` tools' `fields` docs mention the `formattedString` value shape (`{"isFormatted": bool, "text": str}`) or the base64 data-URI pattern.
- **Document tree node mutation** — POST (add) is wrapped via `add_document_tree_nodes`, but PUT on `/nodes` (reorder, re-point existing nodes) is not.
- **Link editing (PUT on `/links`)** — **intentionally not wrapped** for v1. Links can be added (POST via `create_*_links`) and read (GET via `list_*_links`), but there is no tool that does PUT on `/{resource}/{itemID}/links`: a PUT replaces an item's entire link collection wholesale, risking broken traceability links or stranded empty link objects, and link editing wasn't in the initial MCP requirements. (An `update_*_links` tool existed briefly and was removed.)
- **Workflow transitions** — see the *Workflow events limitation* note below; this one is blocked upstream in `helix-alm-rest-api`, not just unwrapped here.

**Workflow events limitation**: For items with workflow (requirements, issues, etc.), the REST API exposes only *applied* events via `GET /{projectID}/<resource>/{id}/events`. It does **not** expose available transitions out of the current state. Workflow events are not currently exposed as MCP tools.

## Tool-specific notes

Tools are defined by `@mcp.tool()` decorators in `perforce_alm_mcp.py`. For the full categorized inventory, see the tool table in `README.md`; read individual docstrings in the script for current signatures. The notes below capture gotchas that aren't obvious from the code or the REST spec.

`update_requirements` and `update_testcases` are list-based bulk endpoints (pass a length-1 list for single-item updates); sub-object envelope wrapping is automatic per item (see **Tool output conventions**). There is no project-scoped GET-list tool for requirements, documents, or test cases — `get_*_by_query` handle both filtered queries and unfiltered listings (call with no args to list all). `submit_automation_build` is the entry point for pushing externally-parsed JUnit/xUnit results; this server does not include an XML parser — the caller (model or a helper script) is responsible for mapping XML to the `results` array shape documented in the tool.

`get_document_tree` only returns tree-position data (`id`, `outlineNumber`, `tag`, `requirementID`, `requirementLink`) per node — it does **not** include requirement field values. To get those, follow up with `get_requirement` per `requirementID` or batch via `get_requirements_by_query`. To pull a full tree in one call, pass both `expand=["nodes"]` and `recursive=True`; either flag alone returns an incomplete response (see the tool's docstring for details).

`add_document_tree_nodes` is the one tool in the suite that intentionally wraps **two** REST endpoints — POST `/nodes` (top level) and POST `/nodes/{nodeID}/childNodes` (under a parent) — selected by whether `parent_node_id` is 0 or non-zero. The body shape and response wrapper key differ between the two (`nodesData` vs `childNodesData`), and the tool builds the right one based on the parameter. (PUT on `/nodes` — mutating existing nodes — is not wrapped; see **Known unwrapped surfaces**.)

**Attachments**: `list_*_attachments` (GET `/{resource}/{itemID}/attachments`) returns metadata only — an `AttachmentContainer` (`{self, attachmentsData: [...]}`), including each attachment's `encodedFileID`. `upload_*_attachment` (POST) uploads a file from a `file_path` **on the machine running the server** (not the caller's machine) and returns an `AttachmentStubHolder` (`{attachmentsData: [...]}`). `file_path` is confined to a single root directory (`PERFORCE_ALM_MCP_UPLOAD_DIR`, default a folder under the system temp directory) via `_resolve_under_root()` inside `_upload_attachment_request()` — the one choke point all four upload tools funnel through — so a prompt-injected `file_path` can't be steered into reading an arbitrary file off the server host; a path resolving outside that root raises before any token/network call is made (hardened in response to a reported path-traversal/arbitrary-file defect, alongside the symmetric `download_attachment` hardening below). Both response shapes carry the REST API's raw `content` href per attachment (`https://.../files/{encodedFileID}`), but all 8 of these tools strip it via `_strip_attachment_content()` before returning: the href requires the same Bearer token the calling LLM doesn't have, so it's dead weight — `encodedFileID` is the field that's actually actionable, via `download_attachment`. This is the one deliberate exception to the "pass the REST response through verbatim" convention for these tools. The same `content` href also appears embedded under the `attachments` key whenever `get_requirement`/`get_requirements_by_query`, `get_issue`/`get_issues_by_query`, `get_testcase`/`get_testcases_by_query`, or `get_document`/`get_documents_by_query` are called with `expand=["attachments"]` — that sub-object is the same `AttachmentContainer` shape as `list_*_attachments`. These 8 tools strip it too, via `_strip_expanded_attachments()` (a thin per-item wrapper around `_strip_attachment_content()`), so the dead href never reaches the caller regardless of which of these 16 tools (or `expand` combination) surfaced it. Issues are a special case on top of that: a `FoundByRecord` carries its own nested `attachments` container, separate from the issue-level one, so `expand=["foundByRecords"]` embeds a `content` href per found-by record too. `get_issue`/`get_issues_by_query` route through `_strip_issue_expanded_attachments()` instead of the plain per-item wrapper — it strips the issue-level `attachments` and then iterates `foundByRecords.foundByRecordsData`, stripping each record's own `attachments`. Coverage differs by type: requirements/documents/test cases have both GET (`list_*_attachments`) and POST (`upload_*_attachment`) directly on the item; **issues have GET on the item (`list_issue_attachments`, aggregating across all found-by records) but POST only on a found-by record** (`upload_issue_found_by_attachment`, wrapping `/issues/{itemID}/foundByRecords/{foundByRecordID}/attachments` — there is no item-level issue attachment-upload endpoint, only found-by-record- and event-level ones, and only the former is wrapped); **automation suites have neither** (no attachment endpoint exists). **POST never works for attachments at create time, for any resource type**: none of `create_requirements`/`create_testcases`/`create_documents`/`create_issues` expose an `attachments` argument — the REST create endpoint silently discards any `attachmentsData` payload (top-level, or nested under a `foundByRecords` item for issues) with no error. For issues, add the attachment after creation with `upload_issue_found_by_attachment` once a found-by record exists. **PUT never works for attachments either, for any resource type**: `update_requirements`/`update_testcases`/`update_documents`/`update_issues` all reject an `attachments` key rather than send it — the REST update endpoint silently discards the payload (returns success, changes nothing), confirmed by uploading a real attachment to a requirement/test case/document, PUTting an empty list (and separately a garbage attachment ID), and confirming the attachment set was unchanged in both cases. `upload_*_attachment` is the only way to add one; there is no endpoint (wrapped or otherwise) to edit or remove an existing attachment. Upload is the one endpoint family that is **`multipart/form-data`**, not JSON — it can't go through `_token_authenticated_request`. It uses the dedicated `_upload_attachment_request()` helper, which hand-builds the multipart body (field name `fileUpload`, a random boundary) and shares SSL/error handling with `_send_request` via the extracted `_execute_request()`. If you add a new attachment-upload tool, route it through `_upload_attachment_request`, not the JSON helpers. Non-ASCII filenames get RFC 2231 encoding (`filename*=UTF-8''<percent-encoded>`) instead of a plain quoted `filename="..."`: a plain quoted-string filename is US-ASCII only per RFC 7578 → RFC 2183, and at least one real server decodes raw UTF-8 bytes there byte-by-byte as Latin-1, silently corrupting the stored name.

**Downloading attachments**: `download_attachment` (GET `/{projectID}/files/{encodedFileID}`) is the single generic download endpoint — every attachment, on every resource type and sub-resource (top-level item attachments, event attachments, found-by-record attachments, etc.), resolves through this one path keyed by `encodedFileID`, so there is no per-resource-type `download_*_attachment` family the way there is for uploads. It takes an optional `destination_dir` and writes the file to disk **on the machine running the server**, returning `{"destination_path", "filename", "bytes_written"}` rather than the file bytes themselves — the mirror image of `upload_*_attachment` reading from a server-local `file_path`, keeping binary content off the MCP/JSON response path in both directions. The endpoint's response is raw bytes even though the OpenAPI spec labels its content type `application/json`, so it can't go through the JSON-decoding request helpers. `_execute_request` was split into `_execute_raw_request` (send the request, return raw bytes or, with `with_headers=True`, `(bytes, response_headers)`; owns the SSL/HTTPError handling) and a thin `_execute_request` wrapper that JSON-decodes bytes-only responses; `_download_file_request()` calls the raw variant with `with_headers=True` and returns `(bytes, filename)`, where `filename` is parsed from the response's `Content-Disposition` header (`None` if absent), Bearer-token authenticated like every other project-scoped call.

**Attachment path confinement**: originally `destination_path` was a full file path chosen entirely by the caller, with no validation — a prompt-injected path (including `../` traversal) could make the server overwrite an arbitrary file it had write access to, anywhere on the host. The tool was redesigned so the LLM no longer controls the destination filename at all: `destination_dir` names only an optional sub-directory, resolved and verified to stay inside `_download_root()` (`PERFORCE_ALM_MCP_DOWNLOAD_DIR`, default a folder under the system temp directory) via `_resolve_under_root()` — the same helper used on the upload side. The on-disk filename instead comes from the download's `Content-Disposition` header, but that header value is itself attacker-supplied (whoever uploaded the attachment set it), so it's reduced to a bare leaf name via `_safe_leaf_name()` (strips directory components, rejects `.`/`..`/empty/NUL) before being joined onto the confined directory, falling back to a sanitized `encoded_file_id` when the header is absent. `_resolve_under_root()`'s `realpath`-based check also closes off symlink escapes, not just literal `../` sequences.

**`_safe_leaf_name()` hardened further**: a fuzz pass against the invariant that `os.path.join(target_dir, leaf)` must never resolve outside `target_dir` found no confinement escape, but surfaced several within-root write anomalies and false-success reports from a header-controlled name. `_safe_leaf_name()` now uses `ntpath` unconditionally (not `os.path`/`posixpath`) so a Docker/Linux deployment reduces a name identically to a native Windows install — `posixpath.basename` doesn't treat `\` as a separator, so a `..\..\win.ini` payload would otherwise survive intact on Linux; `.replace("\\", "/")` before the `ntpath.basename()` call handles the equivalent case on native Windows, where `ntpath.basename` already understands `\` but a leading normalization keeps the two code paths identical. It also strips an NTFS alternate-data-stream suffix (`report.txt:ads` → `report.txt`; the `:` split must happen after `basename`, not before, or `C:evil.txt` truncates to `C`), rejects Windows-reserved device names via `ntpath.isreserved()` (`NUL`, `con.txt`, `LPT1`, etc. — these previously passed through, and opening one on Windows raises no error but silently writes nothing to disk, so the tool reported success for a write that never happened), and truncates a name longer than `_MAX_LEAF_NAME` (200) while preserving its extension, avoiding a bare `OSError` from exceeding `MAX_PATH`. `.strip()` is applied to the whole leaf *before* the `.`/`..` check specifically because doing it after would let `" .. "` (with padding spaces) slip through as a non-empty, non-`".."` string. Sanitization runs after `_download_file_request()`'s RFC 2231 percent-decoding (see above) — decoding first and sanitizing second is required, since sanitizing a still-encoded `filename*=UTF-8''%2E%2E%5C...` string would let an encoded traversal payload pass through untouched. `ntpath.isreserved("trail.")` is also `True` (Windows silently strips trailing dots), so a name like `trail.` now falls back to the sanitized `encoded_file_id` rather than writing under a name that doesn't match the reported `destination_path` — a conscious tradeoff over the alternative of `rstrip(". ")`-ing it into a real (but altered) name.

**Found-by mirror fields**: On an issue, Description, Date Found, Version Found, Steps to Reproduce, Reproducible, Test Config, Other Hardware and Software, and Found By appear in the generic `fields` array (readable via `get_issue`/`get_issues_by_query`) but are actually read-only mirrors of the issue's first found-by record (`foundByRecords[0]`) — writing one via `fields` silently no-ops (success, no change). Created via `found_by_records`, the mirrored labels above show the same values in the issue's `fields` array; a follow-up `update_issues` PUT targeting `Description`/`Steps to Reproduce` via `fields` returns success but leaves both values unchanged, while the same PUT targeting `foundByRecords` (by the found-by record's `id`) changes them correctly. The only way to set them is `found_by_records`'s fixed keys (`dateFound`, `versionFound`, `description`, `reproduced`, `steps`, `testConfig`, `otherConfig`, `foundBy`), each shape verified against the OpenAPI spec's `FoundByRecord`/`TextField`/`MenuItem`/`User` schemas — documented canonically in `create_issues`' `found_by_records` argument (full per-key shapes plus a complete example), cross-referenced from `update_issues`. `create_issues`/`update_issues` enforce nothing at write time here — a `fields` entry using one of these labels still silently no-ops; the docstrings are the sole line of defense on the write side, by design (see below).

On the read side, `get_issue`/`get_issues_by_query` tag each mirrored `fields` entry with an extra `foundByRecordKey` (e.g. `"foundByRecordKey": "description"`) naming the `found_by_records`/`foundByRecords` key that actually controls it, via the shared `_ISSUE_FOUND_BY_MIRROR_FIELD_IDS` map — keyed by field **id**, not label — and `_decorate_found_by_mirror_fields()` helper. These ids are fixed "inherent field" constants baked into the ALM server, not per-project row ids: Perforce ALM reserves ids 0-199 for built-in fields, universally, across every project (see `defectField_Description`/`defectField_DateFound`/etc. in the ALM server's `common/TestTrack/CDefect.h`; custom fields start at id 300 via `kCustomFields_BaseFieldID` and are the ones that vary per project). Confirmed against a live project's `GET /issues` response: Description=54, Date Found=8, Version Found=12, Steps to Reproduce=58, Reproducible=11, Test Config=13, Other Hardware and Software=64, Found By=9 — an exact match to the server constants, including the id-300 custom-field boundary. Because the id is fixed rather than the label, this tag survives a project renaming any of these fields (an earlier label-keyed version of this map didn't: it matched the *default* label text case-insensitively, and lost the tag entirely once a project renamed a field away from that default). Write-time enforcement (rejecting a `fields` entry that targets one of these) is still deliberately **not** added: a `fields` entry can identify a field by either `id` or `label`, and while an `id`-supplied entry could now be checked exactly against this same map, a `label`-supplied entry still can't be verified without an extra lookup — the docstrings remain the sole line of defense on the write side.

**`foundByRecords` wholesale-replace cascade-deletes attachments**: `update_issues`' `foundByRecords` argument replaces an issue's entire found-by collection wholesale (see the tool's docstring) — any existing record whose `id` is omitted from the list is deleted. This cascades to attachments: a file uploaded to a found-by record via `upload_issue_found_by_attachment` is silently deleted along with it when a follow-up `update_issues` call sends a `foundByRecords` list that omits that record's `id` — `list_issue_attachments` confirms the attachment is gone afterward. There is no separate warning or confirmation; the same care needed around losing found-by data (always include every `id` you want to keep) also protects any attachments hanging off those records.

**`folders` wholesale-replace on all four `update_*` tools** (originally reported against `update_documents`): the `folders` argument on `update_requirements`/`update_testcases`/`update_issues`/`update_documents` REPLACES an item's entire folder-placement collection wholesale, same PUT-replace semantics as `links`/`foundByRecords`/`steps` — it is not additive. Omitting `folders` from the payload leaves existing placements untouched, but passing `folders: []` silently removes the item from every folder it was in, filing it nowhere; the call still returns a normal success response with no warning. All four tools' docstrings now document this explicitly (a `Note:` paragraph plus a "Replaces ALL existing folder placements" reminder on the `folders` Args entry) — the underlying wrap logic (`item["folders"] = {"foldersData": ...}`) is identical across all four, so the fix was applied uniformly rather than only to the reported tool.

**`folders` replace is also non-atomic on failure, and the REST API signals this via HTTP 206**: an invalid folder path/ID in the `folders` list doesn't cleanly fail the whole item — the server removes the item's existing placements first, then applies every valid entry in the list; an invalid entry is simply skipped and reported, it does **not** stop processing of the rest of the list (confirmed empirically: a `folders` list of `[valid, invalid, valid]` applies both valid entries, including the one listed after the invalid one — it is not "everything up to the first failure"). So the item can end up filed in some, all, or none of the requested folders, with its original placements already gone regardless, even on a "failed" call. The REST API surfaces this as a 206 partial-success status (schema: `PartialUpdated*Response`, body carries a top-level `errors` array alongside the item array) rather than a clean 4xx. All four `update_*` tools detect this and prepend a top-level `"warning"` key to the JSON response instead of passing it through silently — a deliberate, documented break from the project's usual verbatim-passthrough convention, justified because staying silent here loses data. Implementation: `_execute_raw_request` gained a `with_status` flag (mirroring the existing `with_headers` flag used by `_download_file_request`) to capture `resp.status`; a new `_token_authenticated_request_with_status()` hand-builds the request the same way `_upload_attachment_request`/`_download_file_request` already do — rather than adding `with_status` to the widely-shared `_send_request`/`_token_authenticated_request` — specifically so the `token_req` fixture's dict-only return contract, relied on by every other tool's tests, stays untouched; the affected tools use a dedicated `token_req_with_status` fixture instead. `_folders_partial_success_warning(status, data, had_folders, is_create=False)` decides whether to warn: it fires on `status == 206` or a non-empty `errors` array (the status code and the errors array aren't guaranteed to agree, so both are checked), and only when the request actually included `folders` for at least one item, so a 206 unrelated to folders doesn't claim a folders risk that isn't there.

**The same non-atomic-folders behavior applies to `create_*` (POST), not just `update_*` (PUT)**: the OpenAPI spec documents the same 206 `PartialUpdated*ListResponse` for the create endpoints, and this was confirmed against a live server — a `create_requirements` call with a bogus folder ID still created the requirement (id assigned, normal-looking response) while the folder placement failed with a 404 in `errors`, leaving the new item filed nowhere. There's no prior placement to lose on a create the way there is on an update's wholesale replace, but the same "every valid entry gets applied regardless of position, and the item is still created regardless" behavior holds. The four `create_*` tools (`create_requirements`, `create_issues`, `create_testcases`, `create_documents`) now call `_token_authenticated_request_with_status` instead of `_token_authenticated_request`, and call `_folders_partial_success_warning(status, data, had_folders, is_create=True)` — the `is_create` flag only changes the warning's wording (create has no "existing placements" to describe losing), not the trigger logic. Their tests use the same `token_req_with_status` fixture as the update tools.
